# Menoteam 产品愿景与设计提案

**2026-09-28 · 供团队讨论的 proposal，尚未实现，也未替代当前 V1 规格。** 本文提出一个可被真实使用和验证推翻的产品方向；容量、客户价值、商业需求都还没有实测结论。

## 愿景与产品边界

Menoteam 的目标是支持由多名人类成员与 agents 组成的组织，跨项目持续完成获准的工作。设计目标包含从零搭起、可调度数百个并发 agents 的团队，也让已有 agent 系统的团队接入；“数百”是需逐级验证的目标，不是当前能力。人给出目标、判断与权限边界并承担责任，Menoteam 帮助工作持续推进、接续和验收，减少反复解释、转述、催办与重验；越过边界或需要判断时，带着依据请人决定。

| 执行方式 | 适用团队 |
| --- | --- |
| Menoteam 原生创建、安排并运行 agents；可复用已有 runtime | 从零开始的团队，也包括目标规模达到数百并发 agents 的设计场景 |
| 自带一个或多个 agents，或接入 Paperclip 等完整 agent team | 已有执行环境，希望沿用并连接共同的工作、授权和验收规则的团队 |

两种方式遵循同一套工作、授权、责任、交接和验收规则。Menoteam 可以自己提供执行，也可以使用已有 runtime；不局限于整合其他平台。接入 Paperclip 时，需约定谁负责分解与调度团队内部的工作，避免 Menoteam 和 Paperclip 同时发令。

“human + agents 是一个劳动单元”可帮助理解一个人如何借助 agents 扩展工作，但它不是固定人机配对或必须创建的新实体。一个人可用多个 agents，agent 也可按授权服务多人。协作单位是跨人、跨项目的组织：目标、责任、资源优先级和验收标准都要明确。能力、权限与责任不同；agent 能做某事不代表获准去做，也不会接走人的最终责任。

**状态边界：**当前 V1 提供 shared Work Map 与显式 one-hop routing；Work Map 不运行 agents，也没有原生执行或 Paperclip 集成。本文是待评审的未来方向，未改变 V1 规格。下文的设计目标和验证阶梯不代表已交付能力。

## 四项核心

1. **Work Map。** 团队共享的工作事实、目标、责任、状态、依赖和证据引用；其中包含 Feature Map view，呈现功能/能力、预期行为、入口与验证方式，也记录推进和进度。它让工作可被接手，不增加 public Run 实体，不复制其他系统已有的权威记录。
2. **Actors、责任与权限。** 人、agent、团队及其代表关系可辨认，权限在执行时受项目、动作、资源与期限约束，责任另有明确归属。跨项目依赖不自动扩大数据访问范围，私有会话和个人记忆仍属私有。
3. **Coordination、handoff 与 recovery。** 支持 native 或 external execution，明确工作由谁接受、下一步等待什么、失败如何恢复。送达、接受、执行和完成是不同状态；重复请求不可重复产生副作用，过期 worker 的迟到结果不可覆盖新状态。
4. **Verification。** 结果须绑定产物版本、环境及当时生效的验收规则。独立 verifier 按既定标准检查；标准不适用或无法运行时要报告阻塞或请求授权修改，不能自行降低标准。局部通过不等于集成后完整用户路径通过，修改后须判断旧证据是否失效。

Work Map 连接权威来源，不成为第二套票据系统。核心记录目标、责任、授权、依赖和证据连续性；工程特定的方法与工具保持可替换。工程是默认切入场景，不意味着产品永远只服务 engineering。

## 首次使用、默认方法与规模约束

首次使用应很短：连接一个项目，选择 Menoteam 原生执行或带入已有 agent，确认目标、允许动作和预算，然后开始一项真实工作。默认工程循环负责调查、执行、运行项目检查、独立验证并交付带证据的结果。定制是可选的，团队可调整验收标准、权限边界和工程方法；产品应显示实际生效规则。

先提供工程默认体验，方法采用有版本、可替换的 pstack 实践；DUNE 只作为权威状态、依赖和关键不变量等结构原则的参考，不声称它是可安装 framework，也不把任何团队工具栈写死。团队可以替换 skills、模型、执行 backend 和工程方法；权限、状态归属与证据完整性仍由产品边界保证。应从真实反复失败中逐步沉淀类型、lint、依赖检查或 CI 规则，而非预置所有团队工具或一次性重写项目。

高并发首先是正确性问题。可独立工作的部分需要隔离环境；重复领取必须安全，租约过期、取消或重派后，旧 worker 的迟到结果不能覆盖当前状态。对支持幂等键的 API 操作使用幂等键；若外部操作不支持，或结果未知，先查询并对账，再判断是否重试，不能假设重复调用无害。验证证据绑定产物版本，分支合并后仍要做必要的集成验收。并发还受共享成本与验证资源限制：验证器排队或饱和时减慢新工作，避免未经确认的产出堆积。Agent 不得自行降低验收标准。

测量按阶梯推进：先跑通真实闭环，再测 3–5 个并发执行者，之后逐步测 10、30、100；记录吞吐、排队、冲突、失败恢复、验证资源占用、人工介入和单位成本。成功指标是质量达标且被接受的工作量、人工介入和单位交付成本，不是 PR、agent、任务启动或消息数量。

## MVP 与验证

最小有意义 MVP 应覆盖至少两名人、两个项目，并分别跑通原生执行与接入已有执行环境的路径。先选真实工程工作，走完目标与授权、执行、跨项目交接、独立验证、集成后验收和交付报告。每条证据说明适用版本、环境及未知项。

验证从 3–5 个并发执行者开始，覆盖依赖、环境冲突、重复事件、中断、迟到提交和 verifier 饱和，再逐步扩展至 10/30/100 的受控测量。与强 baseline 比较：团队已有的 issue/PR、CI、skills 和 agent 工具组合需配置到可用水平，并计入接入、维护、模型、runtime 与验收成本。若少量 skills 或现有工具已解决问题，应接受更薄的产品方案。

Paperclip 等产品已有多用户组织能力，竞争存在不证明机会或失败。应验证 Menoteam 是否能在跨人、跨项目和多种执行环境下保持责任、授权及结果证据连续，同时不造成重复调度或第二套状态维护。商业假设仍待研究：谁有迫切问题并愿意付费、相对已有方案的增量价值、团队标准的适配成本、隔离环境成本，以及选择何种 runtime。
